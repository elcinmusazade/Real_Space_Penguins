# Python edition — dual-mode architecture

## Runtime

Python 3.9+, standard library only. `python3 -m ares.server` starts a local `ThreadingHTTPServer` (default `127.0.0.1:8000`) serving **Campaign V2 at `/`** and **Classic Mars V1 at `/classic.html`** with separate JSON APIs. No pip install, database, external model, or NASA API connection is required. `package.json` exists solely for optional preview; **Node is not a runtime requirement**.

## API contract

- `GET /` — loads Campaign V2; `GET /classic.html` loads Classic V1. Other static files use a strict allowlist.
- `GET /api/health` — reports that the Python server is running.
- `GET /api/campaign/catalog` — returns the ship/mission/planet/building/research catalog, `mapSize: 96`, rockets, physics constants, fault and standing-order menus, goals, hazards, orbit tracks and per-turn light times.
- `POST /api/campaign/faults/test` with `{ "design": {"computer": ..., "rules": [...]} }` — lab-tests flight software against all four approach scenarios (and a no-rules baseline).
- `POST /api/campaign/new` with `{ "seed": "HORIZON-01" }` — creates an interplanetary campaign.
- `POST /api/campaign/inspect` with `{ "state": {...}, "hub": "H1", "tile": 4657 }` — read-only survey/build costs, availability/reasons, nominal facility inputs/outputs and site bonuses, using the same helpers as execution.
- `POST /api/campaign/research` with `{ "state": {...} }` — read-only eligibility for every technology, with status, exact cost, prerequisite/lab/field requirements and blocking reasons. Shared with the research action.
- `POST /api/campaign/quote` with `{ "state": {...}, "design": {...} }` — quotes/validates a configured ship and destination.
- `POST /api/campaign/action` with `{ "state": {...}, "action": "launch", "args": {"design": {...}} }` — returns an updated V2 state. Launch takes `confirm: true` to fly a plan that fails a check. Other actions: `shipment`, `explore`, `construct`, `assignCrew`, `research`, `eventChoice` (V2 saves only), `advance`, `setSoftware`, `setOrders`, `prepare`, `repair`.
- `POST /api/campaign/validate` with `{ "state": {...} }` — checks a V2 save envelope.

Classic endpoints (unchanged):

- `POST /api/new` with `{ "seed": "ARES-01", "loadout": [...] }` — returns `{ "ok": true, "state": {...} }`.
- `POST /api/action` with `{ "state": {...}, "action": "explore", "args": [12] }` — validates the prior state and executes one Python rule, returning `{ "ok": true, "state": {...}, "message": "..." }` or a failure.
- `POST /api/validate` with `{ "state": {...} }` — checks a saved game.

Both APIs are stateless: the client submits its current JSON state for each action; Python validates its envelope and returns a new state. Campaign requests accept up to 96 MB to support multiple large maps; Classic retains its 4 MB limit. V2 uses the `ares.first-light.campaign.v2` record in IndexedDB database `ares-first-light`, store `saves`, separate from Classic V1. The storage adapter reads older localStorage campaigns if no IndexedDB record exists, and removes the legacy copy only after the new transaction commits. Database read errors stop initialization instead of overwriting an unreadable save. Browsers without IndexedDB fall back to localStorage and report save failures; that fallback retains its browser quota. **Do not expose this development server as a secure multiplayer or authoritative online competitive service**; client-supplied state is not cryptographically trusted. The development server deliberately binds loopback by default.

## V2 mechanics boundary

New campaigns contain Mars HQ (`H1`, `kind: control`) only, `visitedWorlds: []`, and `nextId: 2`. The catalog exposes `homeWorld: mars`. Earth has no base until mission arrival, never from selecting a preview. Existing saves are not reset or stripped of their hubs. `campaign.js` uses `openHome()` on initialization, explicit reset and the Ares home button: prefer Mars command, then an existing Mars surface base, then historical headquarters as a legacy-save fallback. It clears overlays and initializes valid mission/cargo sources, defaulting new Mars departures to Earth. It does not open or prefetch mission planning. Pending legacy events still open for resolution. `guideSteps()` uses home-base discovery state instead of assuming a second hub. Logistics displays a second-hub prerequisite until two hubs exist, then selects distinct valid cargo endpoints. AURA remains available through its button.

`web/campaign.js` never directly changes authoritative campaign state; its local variables are **UI draft controls** (ship configuration, chosen hub/tile, freight draft, active tab). Python `ares/campaign.py` owns valid actions, economic costs, ship arrivals, settlement generation, hazards, and resource quantities. Each hub has its own inventory. A shipment deducts origin cargo/fuel immediately and credits globally; destination stock and persistent route update **only on arrival**. Every surface hub owns an independent **96×96 map**. Free near-facility scans reveal immediately; regional surveys cost energy and reveal up to nine tiles after 1–3 turns. Remote Sensing reduces that time by one turn (minimum one). Wide-Area Mapping expands newly ordered regional surveys to 5×5 for 8 additional energy. Each order stores its radius; missing legacy radius defaults to 1, so already-paid surveys retain their original footprint. One regional survey runs per hub; nearby scans remain available while it runs. At the 1,000-survey history limit, the oldest completed entry is retired when a new survey starts; discoveries and active orders remain intact. The canvas displays seeded `biome` and `elevation` fields from Python as orbital imagery. The separate `terrain` field remains null until discovery, so deposits and anomalies stay hidden. `ares/surface.py` caches immutable landscapes by seed/world/site and copies metadata into independent saved tiles. Every site has its own camera remembered during play. Building orders cost resources and activate after the specified number of turns. No AP gate exists in V2. Existing 5×5 and 32×32 maps (including Earth control hubs) expand to 96×96 on a deep copy, preserving tile contents and remapping active/completed survey destinations. The seeded landscape extends using the original coordinate origin, so geography in the old central region is unchanged. Classic V1 6×6 maps are unaffected. The `control` kind now works on Mars or Earth independently of planet identity. It receives the original starting stockpile and passive materials/fuel/budget income, a command center and solar array, upkeep and protected command availability without crew consumption or forecast hazards. New landings on Earth are ordinary surface bases with modest outpost inventories and no command income. Empty historical Earth HQ maps still migrate on a deep copy, without resetting progress. The browser selects playable hubs by nonempty tile arrays. Earth bases have no authored surface hazard schedule; forecast generation skips worlds absent from `HAZARDS`.

**Earth travel.** Earth is a destination from non-Earth origins, with authored landing sites and entry/capture assumptions. Its gravitational constant and radius reuse the existing window-builder constants; estimated arrival speed, transfer duration, orbit/landing delta-v and eclipse fault scenario are game assumptions. No new GMAT return-trajectory data is claimed. `flight.transfer()` uses existing symmetric route lengths for Mars→Earth, and Earth→Earth is rejected before looking up a nonexistent table row. New Earth surface/orbital hubs are created only on arrival; flyby/science results do not grant a surface map. Shipments work in both directions. Earth departure hubs retain the existing GMAT windows/launch vehicle checks. Shipyard changes available destinations when the source changes, avoids Earth→Earth drafts, distinguishes estimated departures, and the solar navigator offers a landing action for unowned Earth rather than a nonexistent command shortcut. Displayed map light-times are explicitly Earth-referenced, not Mars-command communication delays.

**Outer-planet maps.** `WORLDS.mapLayer: atmosphere` identifies Jupiter, Saturn, Uranus and Neptune. Each has three authored platform zones and a deterministic 96×96 landscape with five region types, including blocked storm/current cells, condensates and a safe central platform zone. Reuse saved `kind/objective: surface` and the existing map/inspection/construction API; UI labels these as cloud-platform deployments. New deployments require Deep-Space Engineering, a lander/freighter, Survey Station and Environmental Shield; crew habitat payloads are rejected. Orbital hubs still have no sector map, and science/flyby results create no platform. Arrival, damage, repair, forecasts, standing orders and paid shipments reuse Python rules. Existing saves need no reset.

Platform command cores generate 6 energy before consumers, with condition scaling. Weak solar multipliers and Saturn ring-shadow penalties make power expansion meaningful. `ice` remains the saved resource code for condensates; `ridge` represents rich aerosols. Cloud Condensers and Atmospheric Refineries use existing extractor/drill IDs, costs and shared production rules with world-specific UI names; these yields/technology are fictional. Elevation represents cloud-layer relief, not ground. Canvas palettes, drifting ribbons, storm swirls and buoyant facility pods are cosmetic, and picking stays fixed; pause/reduced motion/hidden tabs suppress ambient motion.

Outer-planet transfers use explicit symmetric route durations and game-estimate arrival speeds. Capture uses an explicit game allowance instead of invented planetary constants. Earth launches to these four destinations use labelled estimated C3/direction plus existing vehicle mass checks; `upcoming()` returns no fabricated GMAT windows. `gmatDestinations` controls Shipyard attribution, and `estimatedLightWorlds` marks the new fixed light-time approximations. The four-destination GMAT table is unchanged.

**Campaign rules V3.** One turn is 90 days from 2028-07-01. Earth launches to Mars, Venus, Mercury and Europa read the turn's row of `campaign_windows.json`: `efficient` (lowest total delta-v), `balanced` (lowest delta-v within ±28.5° declination) or `fast`; `assist` (Mercury/Europa) leaves on that turn's Venus transfer, then uses game-estimate flyby timing. Launch mass = hull dry + engine + payload + flight computer + propellant (1 fuel unit = 25 kg) and must fit the rocket's capacity at that C3; propellant gives delta-v by the rocket equation; Mars/Venus landers enter directly, Mercury/Europa need capture first. At arrival the mission's saved flight software runs the destination scenario at a seeded 85-125% intensity: lost / degraded (module lost, damaged base, off-target landing, half science) / nominal. Each turn, surface hubs evaluate standing orders, then any forecast hazard, production, upkeep (1 material per two buildings, else wear), and crew needs; crew health 0 loses the base, three unpowered turns darken an uncrewed one. Every 4 turns a review scores the year and moves the budget between 4 and 30 credits per turn. AURA is state-aware authored text in the UI, not model-generated dialogue.

Solar navigation keeps open/closed state, inspected body, route visibility, and camera position outside the campaign save. It uses existing map, mission-planning, and cargo actions. Background controls are inert while the dialog is open, focus stays in the dialog, and closing restores focus to its launcher. The Sun is an inspectable landmark; all eight planets and Europa have maps and mission actions. Europa remains a moon of Jupiter. The destination footer is derived from catalog coverage and scrolls horizontally. Orbit paths and transit markers are schematic navigation graphics, not the GMAT trajectory renderer.

Solar chart motion uses a view-only `requestAnimationFrame` loop to move complete body groups along fitted schematic ellipses. `solarPositions` computes positions from elapsed visual time; Europa's orbit is relative to moving Jupiter. Labels and hit targets move with their bodies, and route curves/markers follow the endpoints while retaining their turn-based progress fraction. CSS separately animates surface textures and Sun/star/background effects. `campaign.js` retains a pause flag and visual time; `mountSolarSystem` restores phases across re-renders, pauses for hidden tabs/reduced motion/hover/keyboard focus, and cancels frames/listeners on destruction. No game timers, save fields or runtime dependencies are added. The optional Node regression in `tests/test_solar_navigation.py` checks actual SVG position updates and the motion lifecycle.

Living surface rendering shares corner heights between tiles, hides permanent grid outlines outside construction/selection, and picks sectors against their projected polygons. Atmosphere, water and foliage animation does not advance game time; Pause, reduced motion and hidden tabs freeze it. Arrow keys select sectors; drag, zoom, minimap and fit controls remain. Fit/minimum zoom adapts to the larger map and viewport size. Offscreen sectors are culled before elevation geometry; below 0.45 scale, subpixel scenery/textures are omitted. The minimap outlines the viewport. Center selections derive from the catalog size. Canvas listeners and frames are cleaned up on remount. Selecting a sector only inspects it; explicit **Scan Sector / Start Regional Survey / Build Here** buttons spend resources. The controller discards stale inspection replies when selection or authoritative state changes.

Surface construction uses biome preparation costs and rejects open water, lava/ice fissures and discovered hazards. Water plants accept discovered ice or dry land beside Earth water. Nominal production comes from `surface.production` for both the inspector and the turn engine. Solar and reactor generation run first, followed by water, oxygen, food, heat, habitat/shield support, mining and research; tile ID breaks ties. Each facility requires all its inputs or stays idle without partial spending. Existing condition, weather, orders, upkeep, crew consumption and stock caps still apply. UI rates are explicitly full-condition rates before weather/orders/shortages.

Old `expeditions` and hub `roverBusyUntil` fields migrate to `surveys` and `surveyUntil`; rover counts are removed. The `rover` payload becomes `survey` (same mass/cost), and `robotics` becomes `surveying`, preserving purchased/research-in-progress records and mission arrival dates. Missing geography is added without changing old revealed deposits or buildings; an old building that would otherwise be on blocked geography gets a safe landing plain. Migration is idempotent and does not mutate caller saves. Classic rover fields remain independent.

## Research progression

`RESEARCH` defines four branches and four tiers (16 technologies), descriptions/effects, costs, duration and prerequisite IDs. `TECH_UNLOCKS` maps engines, hulls, launchers, destinations and facilities to research. `research.plan()` is shared by inspection and action execution: completed/active/locked/busy/funding/ready states, one active project, and costs deducted exactly once. Labs must belong to an active hub, be switched on, have positive condition and be online this turn. Lab eligibility is checked when starting a project, not continuously; it does not promise enough energy for production. Advanced requirements include 12 newly discovered sectors or a completed mission reaching Mars; both visited-world evidence and a completed mission record are required, so the starting home world cannot satisfy this by itself. Paid projects complete on their saved turn even if their original prerequisites differ from the current catalog.

`campaign.mission_quote()` gates only new designs (and therefore launches), without changing `flight.assess()` or the physical spacecraft calculations. Existing flights and built facilities continue operating. Precision Navigation reduces fuel-stock accounting only, not loaded propellant or delta-v. Basic Earth and Mars missions stay open; Europa surface missions require Deep-Space Engineering, but remote/orbital missions do not. Construction plans gate reactors, apply Modular Construction's material discount including preparation with rounded totals, and reduce new build duration by one turn (minimum one). The inspector shows the actual marginal preparation cost after discount.

`surface.production(..., tech)` supplies identical nominal rates to inspection and turn resolution: solar +35%, drill +2 materials/−1 energy, labs +4 science, greenhouses +4 food/−1 water, water/oxygen +50%. Crew consumption and forecast hazard mitigation are applied in the turn engine. Reactors use 2 water and 2 materials from stored reserves to generate 28 energy before consumers, independent of sunlight; insufficient inputs cause an idle turn with no partial spending. Normal condition, stock caps and upkeep still apply. Benefits activate when research completes, after that turn's production; pending construction/surveys retain their saved timing/footprint. These are fictional gameplay coefficients.

The tree renderer changes no campaign state. It renders all nodes plus dependency lines, including cross-branch paths routed in gutters. Selection highlights ancestors and opens benefits/requirements/children; native buttons support keyboard selection, with zoom/Fit and native scrolling. `campaign.js` fetches eligibility when opening research or receiving new authoritative state, discards stale responses, restores tree scroll/focus on rendering and submits ordinary research/advance actions. Locked build/mission options link to the required node; lab requirements link back to the current home base (Mars in new campaigns). Error/retry and loading states keep spending disabled until a valid plan arrives. Existing researched IDs and the robotics→surveying migration remain valid.

`tests/test_research.py` covers graph integrity, costs/timing, eligibility, compatibility, production, hazards, construction, survey footprints, equipment gates and a Mars-home lab-to-reactor playthrough. `tests/test_mars_home.py` covers command funding without Earth, paid flight/arrival, Earth construction, orbital/flyby restrictions, site reservations, delayed shipments and a return mission from Earth. `tests/mars_start_check.mjs` covers fresh/resumed/reset navigation, legacy saves, explicit mission planning, post-landing Earth access and origin changes. `tests/tech_tree_check.mjs` checks actual view/controller code, topology, no connector/card intersections, escaping, immutable rendering, zoom/navigation, API action submission, stale responses and retry. HTTP coverage verifies the new assets and endpoint.

## Classic V1 compatibility boundary

The interface was ported from the original JavaScript edition. `web/engine-view.js` remains the old engine for synchronous, **read-only** calculations used by UI views (including construction previews and forecast displays). It still contains old mutation functions as legacy source, but `web/bridge.js` overrides the exported names of all state-changing actions. The UI imports `bridge.js`, never the old engine directly. If you adjust operating rules in Python, update the read-only JS projections or migrate those projections into Python API responses. No JavaScript mutation fallback is permitted when Python fails.

Python uses the original seeded map algorithm (FNV-1a + Mulberry32), compatible save shape, and equivalent resource-rounding semantics. Tests compare creation and a complete victorious mission against the original JS engine when Node is available.

## Classic V1 operating priority

The engine's one resource-allocation plan underlies production, forecasts, and end-of-Sol resolution:

1. Online solar arrays generate power.
2. Reserve habitat/crew needs first; water recovery depends on sufficient power, but crew consumption still occurs.
3. Optional producers run in order: **water extractors, oxygen recyclers, greenhouses, laboratories, shields, batteries**. Within each building type, lower tile IDs operate first.
4. A producer lacking its complete energy/water inputs is idle, with zero output and zero optional operating consumption.
5. After the Sol resolves, apply health consequences and storage caps. A just-built structure starts operating on the **next** Sol.

The priority is a transparent game rule, not an asserted NASA operating procedure.

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q ares

```

If Node.js is available, `node --check web/campaign.js`, `node --check web/app.js`, and `node --check web/bridge.js` are useful syntax checks, and Python's parity test exercises `web/engine-view.js`.
